01

What Cloudflare OS actually is

Cloudflare OS is Cloudflare's internal AI workspace, open-sourced under Apache-2.0 on August 5, 2026 after roughly a year of internal use by thousands of employees across sales, engineering, IT, investor relations, and business development. It is a browser-based agent workspace built on Cloudflare Workers: every employee gets a chat-driven workspace grounded in the company's curated knowledge, with agents that produce living documents, build small applications, and act on external systems — under a capability-based security model.

Two things make it genuinely different from "a chatbot with connectors," and both matter commercially:

  • Per-user sandboxed software ("Apps" / "Gadgets"). Instead of one shared SaaS instance, every user runs their own copy of each app — a Dynamic Worker with its own SQLite database (Durable Object Facets). Agents can modify a user's copy without affecting anyone else. Sharing an app gives real-time collaboration on shared state with two roles (build — edit code, use AI chat, manage bindings; use — interact with the UI only); sharing its Blueprint gives someone their own fresh copy. Collaborators always use their own model budgets and their own third-party connections — sharing an app never leaks the owner's external accounts.
  • Gatekeepers. Every external system is reached only through a service-specific Worker that holds the credential, enforces policy, records everything read, and mediates anything with an externally visible side effect. Agents and apps start with access to nothing. This is the piece that makes "centralized, controlled AI" a real claim rather than a slide.

The security model, in one paragraph

Agents and apps start with zero access; capabilities are granted explicitly and credentials never touch agent code. The platform records every resource an agent observes, and those observations travel with the work — when someone opens a shared workspace or document, Gatekeepers verify that person's access to every observed resource before showing it. Server code runs with outbound networking disabled; sensitive reads can taint a session and restrict what the agent may do next (no external sends, no new collaborators). Side effects — merging a PR, sending an email, issuing a refund — can be queued behind human approval, and agents keep working on a simulated outcome while approval is pending. Share links are stored as HMAC hashes and revocable, with sessions force-restarted when access changes. For regulated clients, the observation log is the audit trail.

What ships today

The core repo (cloudflare/cloudflare-os), a hosted deploy flow at os.cloudflare.app/deploy, and a starter deployment repo (cloudflare/cloudflare-os-starter) that wraps a pinned release with your branding, sign-in, routes, custom Gatekeepers, and upgrade control — customization without patching upstream. Stock Gatekeepers exist for GitHub, Google APIs, Slack, Notion, Confluence, Supabase, Email Workers, the Cloudflare API, Home Assistant, Spotify, and ZoomInfo. The platform also connects to existing MCP servers your client's vendors already publish, governed through MCP Server Portals (Cloudflare One) — see the decision tree in Section 02. Everything not covered by either — much of the CRM/QBO/EMR/ERP long tail — is a custom Gatekeeper you build. That build-vs-connect gap is the core of the services business.

Maturity check — set expectations honestly

  • v2 is a complete rewrite, self-described as early access with "many rough edges"; upstream accepts only trivial PRs right now. Pin releases and plan deliberate upgrade windows — never track main for a client.
  • The managed dashboard product, container support, and Slack-embedded workspaces are roadmap, not shipped. Sell what exists.
  • Cloudflare's named implementation partners are Presidio and Happy Cog — the partner motion is real and sanctioned; pursue it formally (Section 03).
  • It runs on workerd, the open-source runtime, under Apache-2.0 — a genuine self-host / exit path and a permissive license you can build a proprietary practice on.

Build order for integrations — cheapest trust first

Stock Gatekeepers (Google email/calendar, Slack, Notion/Confluence) land in days and produce visible wins immediately. Custom Gatekeepers follow in value order: CRM → QuickBooks Online → merchant processor → line-of-business system. Start every Gatekeeper read-only; add writes behind approval queues only after the pilot proves the read path.

Gatekeeper vs. MCP server — always check the cheapest governed path first

MCP v2 (spec 2026-07-28) made MCP servers stateless plain-HTTP workloads — they run as ordinary Workers, and vendors are shipping official remote servers fast (Cloudflare alone publishes 13). Cloudflare OS supports both integration paths natively. The decision tree, per system:

  1. Stock Gatekeeper exists → use it (config, ~half a day).
  2. Vendor publishes a remote MCP server → connect it through an MCP Server Portal (Cloudflare One AI controls): SSO-gated, per-tool scoped, logged — configuration instead of code, and the vendor maintains the integration.
  3. Neither → custom Gatekeeper from the practice library.

Where custom Gatekeepers still win even when an MCP server exists: your own approval-queue semantics on side-effectful tools, tight typed scoping (per-matter, per-realm, minimum-necessary PHI), on-prem reach via Tunnel, and policy that belongs to you rather than the vendor's tool surface. Rule of thumb: MCP for reads and vendor-maintained breadth; Gatekeepers for writes, walls, and anything the client must be able to audit on their own terms. Price portal connections like stock-gatekeeper config, not like builds.

03

Before the first client — building the practice

Everything in this section is built once, on your own account and your own time, and amortized across every client. Budget 3–5 weeks before the first serious pitch. The single most important asset is a working showroom — this product demos far better than it describes.

The showroom deployment

Deploy your own tenant from the starter repo (or bootstrap via os.cloudflare.app/deploy, then migrate to starter-managed) at your own domain. Seed it with fictional-but-realistic data for your two lead verticals — a fake clinic, a fake job shop — and build the 20-minute demo arc: ask a question grounded in company knowledge → generate a live document → have the agent build a small gadget → trigger an action that lands in the approval queue → open the observation log. The approval queue and the audit trail are the close; decision-makers have seen chatbots, they have not seen governed side effects.

The reusable IP library

Keep a private practice monorepo, versioned like a product. Per-client work becomes instantiation + policy, not invention:

  • Gatekeeper library — QuickBooks Online, Stripe, HubSpot, Salesforce, Microsoft Graph (M365 mail/calendar), plus one vertical system per target industry. Each with a policy template (scopes, approval rules) and an integration test suite.
  • Skills starter kits — 10–15 skills per vertical (Section 06 lists the workflows they encode), plus a generic Codex template with the section headings every client fills in.
  • Gadget blueprint packs — apps built once in your own OS export as .gadget archives and import into any client deployment (author metadata preserved, each instance gets independent storage and bindings). Curate them on each client's admin-controlled Explore page, so every deployment ships with your vertical app library pre-loaded.
  • Delivery collateral — discovery interview guide and scoring rubric (Section 04), client setup checklist (Section 05), SOW/MSA templates with IP and data-handling clauses, the security one-pager answering Section 10's FAQ, training decks for all four tracks, runbook templates.

Positioning and partnerships

  • Apply to the Cloudflare partner network and reference the sanctioned implementation-partner motion (Presidio, Happy Cog). Being listed matters for mid-market credibility.
  • Run your own practice on Cloudflare OS — your CRM, your QBO, your proposals. It is the best testbed and the best proof. Section 12 maps the full client-acquisition-to-deployment pipeline this grows into.
  • Apache-2.0 means your custom Gatekeepers and skills kits can be proprietary or client-assigned per SOW — decide the default now and put it in the MSA (recommended: client owns their policy config and Codex; you retain the reusable Gatekeeper code, licensed to them perpetually).

Team shape

Solo-operator viable at the start with contractors for training days. The four hats that must be worn: engagement lead (discovery, governance, exec relationship), integration engineer (Gatekeepers, deployment, TypeScript/Workers), knowledge engineer (Codex, skills, retrieval tuning), trainer. First hire when pipeline demands it: the integration engineer.

A full engagement for a mid-market client (25–500 seats) runs 14–16 weeks across eight phases; a small clinic or firm compresses to 8–10 weeks by shrinking discovery and running one integration wave. Phases 3 and 4 deliberately overlap — integrations and knowledge curation are parallel workstreams with different skill sets.

0Week 0

Qualification & readiness

Confirm the client is a fit before selling a build: real volumes of repetitive knowledge work, systems with usable APIs, an executive sponsor who will enforce adoption, and a compliance profile you can serve (HIPAA, SEC/FINRA, attorney confidentiality). Establish who owns the Cloudflare account and what data-protection paperwork is required (BAA for healthcare, DPA generally). Hand over the Section 05 setup checklist now — credential gathering is always the long pole.

Deliverables Engagement scope, compliance checklist, prerequisites list issued.
Exit criteria Signed scope; sponsor named; Cloudflare account (or plan to create one) confirmed.
1Weeks 1–3

Customer discovery

Steal Cloudflare's own internal playbook. Run stakeholder interviews per department, then set up a "magic inbox" — an alias like routine@client.com where employees forward or cc every repetitive task for two weeks. Cluster the contents weekly; that inbox becomes an evidence-based automation catalog in the company's own vocabulary. In parallel, inventory systems and their APIs, and map data sensitivity (what is PHI, privileged, PII, financial).

Interview guide — the ten questions that surface automatable work

  1. Walk me through yesterday morning, task by task.
  2. What do you redo every week or month that feels identical each time?
  3. What takes a new hire longest to learn?
  4. Which emails or messages do you dread, and why?
  5. What information lives only in one person's head?
  6. What reports do you produce — for whom, from which systems, how often?
  7. Where do you wait on approvals, and how long?
  8. Between which systems do you re-key the same data?
  9. If you got five hours back a week, what would you spend them on?
  10. What should never be automated here?

Scoring rubric — rank every candidate use case

  • Value = frequency/week × minutes per occurrence × people affected.
  • Feasibility 1–5: API quality, data accessibility, output verifiability.
  • Risk tier: A read-only · B write behind approval · C external side effects. Pilot from high-value, high-feasibility, tier A/B.
  • Select 3–5 pilot workflows — at least one with a same-week payoff (email/meeting digest class) and one that touches the CRM or books (proves the governed-integration story).
  • Identify 2–4 champions — respected early adopters per department, per Cloudflare's own rollout model. Not necessarily technical; necessarily influential.
Deliverables Use-Case Register (scored), Integration Map, Data Sensitivity & Policy Matrix, Pilot Charter, champion roster.
Exit criteria Sponsor signs the pilot charter and the policy matrix — especially which actions require human approval.
2Weeks 3–4

Foundation deployment

Stand up the platform in the client's Cloudflare account using the starter repo: Node 24 + pnpm 11 + authenticated Wrangler; fill deployment.jsonc (account ID, hostname in an active DNS zone, Access audience, admin emails); pnpm check then pnpm deploy. Configure sign-in for the client's reality: Cloudflare Access bound to their IdP for orgs that have one, or Google OAuth via AUTH_GATEKEEPERS=google with a domain allowlist for small shops — then DISABLE_PASSWORD_AUTH=true. Configure AI Gateway with the agreed model matrix, per-team budgets, and the per-user daily allowance; brand via /admin; verify error reporting and logs land where IT can see them. Stand up a staging deployment at the same time — it is the upgrade-testing target for the life of the account.

Deliverables Production + staging workspaces at client hostnames behind SSO; model/budget policy in effect; observability wired.
Exit criteria Admins and champions sign in with company credentials; a test workspace produces a document; spend shows up attributed in AI Gateway.
3Weeks 4–8

Integration build — Gatekeepers

Connect the systems from the Integration Map, stock first, then custom. Every custom Gatekeeper follows the same discipline: typed bindings for specific resources (this pipeline, this ledger, this matter — never "the whole API"), read-only first, side effects behind an approval queue, and full observation logging. Custom Gatekeepers live in packages/custom-gatekeeper as separate Workers with service bindings, so they deploy and test independently of the OS core — instantiate from your practice library and apply client policy.

  • Wave 1 (stock): email + calendar (Google Gatekeeper; Microsoft 365 is custom via Graph), Slack, Notion/Confluence.
  • Wave 2 (custom, cross-industry): CRM; QuickBooks Online; merchant processor (Stripe/Square).
  • Wave 3 (custom, vertical): the line-of-business system — ERP, practice management, DMS, EMR, portfolio platform — reached over Mesh/Tunnel if on-prem.
Deliverables Deployed Gatekeepers with policy docs per system; integration test suites; approval-queue routing (who approves what, in Slack/email).
Exit criteria Each pilot workflow can reach every system it needs; a red-team pass confirms agents cannot exceed granted scopes; approvals reach the right humans.
4Weeks 4–8 · parallel

Knowledge & skills curation

This is where the deployment becomes their OS. Cloudflare's stated principle — "the context from the organization matters more than the model" — is the pitch. Build the client's Codex: an authoritative, opinionated guide to how the business works (their Engineering Codex equivalent — for a law firm the practice manual; for a clinic, the front-office and documentation standards). Convert SOPs from the magic inbox into skills files, starting from your vertical kit; load reference corpora into R2 + AI Search; connect the existing wiki through its Gatekeeper; build document/slide templates in the house style.

Deliverables Client Codex v1, 10–25 skills files covering the pilot workflows, retrieval sources live, branded templates.
Exit criteria A champion runs a pilot workflow cold and the agent uses the right vocabulary, process, and sources — verified against the observation log.
5Weeks 8–11

Pilot

5–15 users including all champions, running the 3–5 charter workflows in real work. Instrument from day one: hours saved per workflow (self-reported + sampled), approval-queue latency (slow approvers kill agent value), error/rework rate, and model spend per workspace from AI Gateway. Hold a weekly tuning session: tighten skills, adjust Gatekeeper policy, promote useful one-off gadgets into shared Blueprints.

Deliverables Weekly metrics, revised skills/policies, pilot report with go/no-go per workflow.
Exit criteria ≥3 workflows with measured wins champions will vouch for; spend per user within budget; zero unauthorized-access findings in the observation logs.
6Weeks 11–14

Rollout & training

Department-by-department waves, each opened by its champion demoing real wins from the pilot — never a generic AI demo. Run the role-based curriculum (Section 08), stand up champion office hours, and seed the Blueprint library so each new department starts from working examples. Publish the internal directory of what the OS can do, in the client's own vocabulary.

Deliverables All-hands launch, per-department sessions, Blueprint library, internal capability directory, office-hours cadence.
Exit criteria ≥60% weekly active usage in rolled-out departments; each department has one champion and at least one department-specific workflow live.
7Weeks 14–16

Handoff & operations

Transfer ownership deliberately against the signable acceptance checklist in Section 08. Admin training covers deployment.jsonc, Access policy, AI Gateway budgets, Gatekeeper credential rotation, and the upgrade runbook: monthly pinned-release bumps tested in staging before production — non-negotiable while upstream is in heavy development. Establish a client-side governance council (sponsor + IT + one champion per department) that owns the policy matrix, model budgets, and the skills backlog. Rotate every credential you touched. Agree the support tier: full handoff, or managed service.

Deliverables Admin & ops runbooks, upgrade calendar, governance charter, metrics dashboard, 30/60/90-day adoption plan, signed acceptance checklist, support agreement.
Exit criteria Every item on the acceptance checklist demonstrated, not promised.

Client setup checklist — what to collect, in order

Issue this at Phase 0 and chase it weekly; waiting on credentials is the number-one schedule killer. Everything is collected into the client's own systems — you request access, you never become the owner of record for any of it.

Commercial & legal

  • MSA + SOW signed (IP ownership of Gatekeepers/skills per Section 03)
  • DPA; BAA where PHI is in scope (with Cloudflare and with model providers — verify current availability before promising)
  • Named executive sponsor and IT owner with authority to approve the policy matrix

Cloudflare account

  • Client-owned Cloudflare account; Workers Paid plan enabled
  • DNS zone active (or subdomain delegated) for the workspace hostname + a staging hostname
  • Scoped admin seat or API token for your deploy user (revoked at handoff)
  • Wrangler-capable machine or CI runner agreed with IT (Node 24, pnpm 11)

Identity & people

  • IdP admin contact; Access application created, audience tag captured for deployment.jsonc — or Google/GitHub OAuth app credentials if using auth-gatekeeper sign-in
  • Admin email list; full user roster with departments
  • Named approvers per approval queue (payments, outbound sends, filings)
  • Champion roster (2–4) and training calendar holds

Models & budgets

  • Provider decision (Anthropic / OpenAI / Workers AI mix) + API keys issued to the client's own provider accounts
  • AI Gateway created; token with AI Gateway Run and Read permissions
  • Model matrix agreed: which tier for which task class
  • Budgets per team + per-user daily allowance value (DAILY_LLM_CALL_LIMIT)

Per-system credentials (as scoped)

  • QuickBooks Online: Intuit developer app (OAuth2), sandbox company first, then production consent
  • Stripe/Square: restricted API key — read + refund scope only, no key with full account control
  • CRM: HubSpot private app token / Salesforce connected app with scoped profile
  • Google Workspace: OAuth app + admin consent for mail/calendar/Drive scopes in use
  • Microsoft 365: Entra app registration, Graph scopes, admin consent
  • Vertical system credentials (EMR, ERP, DMS, portfolio platform) + Mesh/Tunnel plan if on-prem

Knowledge inputs

  • SOP corpus export (docs, wikis, checklists) with owner per document
  • Wiki access (Notion/Confluence) for the stock Gatekeeper
  • Brand assets + document/slide house templates
  • Magic-inbox alias created and announced by the sponsor

Vertical playbooks

The platform, phases, and governance model are identical across industries — what changes is which Gatekeepers you build, which knowledge you curate, and which regulator is looking over your shoulder. Each playbook lists the integration ring, the knowledge to curate, the first workflows to charter, and the guardrails that make the deployment defensible.

Manufacturing job shops · discrete · light industrial

Systems to gatekeep

  • ERP — NetSuite, Epicor, SAP Business One (quotes, POs, inventory)
  • CMMS / maintenance system
  • MES / production data — read-only, via Mesh/Tunnel for on-prem
  • Supplier & customer email, shared calendars

Knowledge bases

  • Work instructions & SOPs
  • Quality manual (ISO 9001), CAPA history
  • Safety data sheets (SDS)
  • Quote/win history, supplier scorecards

First workflows

  • RFQ triage → draft quote from ERP cost history (approval before send)

Guardrails

  • OT/MES strictly read-only — agents never touch machine control
  • PO issuance and quote sends behind approval queues
  • Pricing data scoped to sales/estimating roles

Wallets angle Sell-side is the interesting play: expose parts availability, spec, or pricing data as an x402-metered API through the Monetization Gateway so distributors' and customers' agents can query (and pay) per call. Buy-side: metered commodity-pricing and logistics data APIs on capped Virtual Wallets.

The Cloudflare Wallets track

Cloudflare Wallets (announced alongside Agents Week 2026) give agents the ability to pay for things. Two constructs: Account Wallets for humans and organizations, and Virtual Wallets for agents operating via API key. Payments ride the x402 protocol — payment attached directly to an HTTP request, settled in stablecoin micropayments — so an agent can try, compare, and buy API services without a human navigating a checkout page. Guardrails are native: each Virtual Wallet carries an allowance, an allowlist, and a maximum transaction size. Identity comes from cloudflare.pay handles (e.g. research.acme.cloudflare.pay) plus Web Bot Auth keypair registration, so merchants can attribute and trust agent traffic. On the sell side, the Monetization Gateway lets a business accept headless micropayments for its own APIs and content.

Three patterns worth building for clients

  1. Governed agent spend (buy-side). Finance owns the Account Wallet; each department or agent gets a Virtual Wallet with a weekly allowance and vendor allowlist — "$100/week of enrichment for the SDR agents," "$50/week of records lookups for intake." Spend is attributed per agent, capped by construction, and reviewable by the same governance council that owns model budgets. This is the natural extension of the AI Gateway budget conversation you're already having in Phase 2.
  2. Monetizing the client's data (sell-side). If the client has data other businesses' agents will want — parts availability, capacity, rate cards, specialized content — the Monetization Gateway turns it into a metered, x402-payable API. For a manufacturer this can be a genuinely new revenue line, and it's a build you deliver as a Worker in the same account. Under MCP v2 the natural shape is an MCP server whose tools are x402-priced — other businesses' agents discover, call, and pay through one protocol stack.
  3. Agent identity for trust (both sides). Register the client's agents with cloudflare.pay handles and Web Bot Auth so their traffic is attributable — increasingly, this is what keeps a legitimate agent from being treated as a hostile bot by the other side.

When to include the track — and when to refuse it

  • Offer it as Phase 8, post-rollout only, and only where real metered spend or a real sell-side story exists. Wallets attached to a platform nobody has adopted yet is a distraction.
  • Stablecoin settlement means treasury and accounting sign-off: who funds the Account Wallet, how spend books into QBO, who reviews the allowlist.
  • For financial-services and healthcare clients, get compliance review first. Position is always: Wallets is for agent-to-service commerce — client funds, patient billing, and card payments stay in existing regulated rails.
  • The product is brand-new. Claim the client's cloudflare.pay handle early (defensive), pilot with small allowances, and treat everything else as reversible.

IT & security FAQ — objection handling

Where does our data live?

In your own Cloudflare account — R2, KV, and Durable Objects you own. We hold no tenancy, no copy, and at handoff no access. Observation logs, documents, and app state are yours.

Who can see our system credentials?

Only the Gatekeeper Workers. Credentials never reach agent code, model providers, or shared artifacts. At handoff, every credential we touched is rotated as part of the signed acceptance checklist.

Do AI providers train on our data?

All model traffic routes through your AI Gateway to the endpoints we configure — enterprise/no-training terms, selected per your policy. The model matrix is yours to change at any time without redeployment.

What stops an agent from doing something it shouldn't?

Agents start with access to nothing; every capability is an explicit grant through a Gatekeeper that scopes resources, logs every read, and queues side effects (sends, payments, filings) behind named human approvers. App servers run with outbound networking disabled.

Can an employee leak data by sharing a workspace or app?

The platform records every resource an agent observed; when someone opens shared work, Gatekeepers verify that person's access to each observed resource — against the viewer's own connected accounts, re-checked on every open so revoked access is caught promptly. Collaborators use their own model budgets and their own third-party connections. Share links are stored hashed and are revocable, with live sessions cut on revocation.

What's the license, and what do we own?

Cloudflare OS is Apache-2.0 — permissive open source. Your deployment config, Codex, skills, and policy are yours outright; custom Gatekeeper code ownership is set in the SOW (default: perpetual license to you, reusable core retained by us).

What if Cloudflare abandons the project?

The pinned release keeps running regardless — nothing phones home. The runtime (workerd) is open source, and the platform can be self-hosted on it. Your exit path exists on day one.

Is this HIPAA / SEC ready?

The architecture supports it — scoped access, audit logs, approval gates, retention export — but paperwork must precede PHI/PII: BAA or DPA with Cloudflare and with each model provider, verified per current terms during Phase 0. Your professionals remain accountable for outputs; the platform makes that accountability auditable.

11

Risks & honest caveats

  • Upstream churn. Early access, heavy development, small-PRs-only. Mitigate: pinned releases, a standing staging deployment, monthly tested upgrades, never promising features off the roadmap (managed dashboard, containers, Slack embedding).
  • You own the Gatekeeper long tail. Stock coverage is thin outside the Google/Slack/Notion core; every CRM/QBO/EMR/ERP connection is code you build and maintain. That's the business — but price maintenance into the retainer, and reuse ruthlessly across clients.
  • Model spend drift. Unbudgeted frontier-model usage is the classic blowup. AI Gateway budgets, the per-user daily allowance, per-tier model matrices, and monthly governance review are the standing defense.
  • Compliance is shared, not transferred. BAAs, retention, and marketing-rule review make the deployment defensible; the client's professionals remain accountable for outputs. Put "humans retain accountability" (Cloudflare's own principle) in the governance charter verbatim.
  • Approval-queue fatigue. If everything needs sign-off, value dies in the queue; if nothing does, trust dies on the first bad send. Tune per workflow during the pilot, and monitor approval latency as a first-class metric.
  • Credential-gathering drag. The most common schedule slip is waiting on client OAuth apps and API keys — issue the Section 05 checklist at Phase 0 and review it weekly with the sponsor.
  • Exit path. Apache-2.0 core on open-source workerd, self-hostable. Document this in every proposal — it converts the lock-in objection into a strength.

Why the four gates are features, not compromises

Outreach approval, the discovery conversation, the signature, and client-held consents are exactly the "agents do the work, humans approve the side effects" model you sell.
